# ADR-0001: V0.3 不做多平台抽象层（不做 ecpcore）

- 状态: 已接受
- 日期: 2026-08-16
- 决策人: 项目维护者（与 AI Coding Agent 讨论后）

## 背景

原始开发规格（modWeCom_v0.1 开发规格 §54）将"钉钉、飞书、统一企业协作平台接口"
列为 V0.3 目标。曾讨论为此建立公共库模块 `ecpcore`（Enterprise Collaboration
Platform），从 modWeCom 中提炼平台无关的接口与引擎，供企业微信/钉钉/飞书三个
模块复用。

## 决策

**不建立 ecpcore，不做多平台抽象。** 钉钉（及飞书）暂不立项。V0.3 的实际投入
方向为：部署到备案域名环境完成 Webhook/OAuth 真实联调，打磨 V0.1/V0.2 功能。

## 理由

1. **抽象的价值来自复用次数**。只有一个平台模块时，接口层没有第二个调用方，
   只会给同一份代码加包装：维护成本增加（改功能动两层），收益为零。这正是
   规格 §2.3"现在禁止过度设计"要防的事。
2. **未来抽离成本被 V0.1 架构压得很低**。平台相关代码已天然收敛在三个文件：
   - `class/wecomapi.class.php` — HTTP、Token 缓存/刷新、所有企业微信端点
   - `class/wecomcrypt.class.php` — 回调签名验证与 AES 加解密
   - `wecom/oauth.php` — OAuth 跳转与回调
   业务层（同步引擎、映射 DAO、Admin 页面、REST API、事件日志）不关心企业微信
   协议。届时把上述三个文件的方法提炼为接口、由 WeComApi 实现，预估一至两个
   工作日，不是重写。
3. **带着真实需求设计接口更可靠**。等第二个平台真立项时，钉钉/飞书的实际 API
   形态会告诉我们接口边界在哪；现在凭想象设计的接口大概率届时要推翻。

## 约束（保持抽离选项开放的纪律）

无论未来是否抽离，以下纪律必须维持（现状已满足，Code Review 时检查）：

1. 业务代码只准调用 `WeComApi` 的公开方法，禁止在业务代码中出现直接 HTTP
   调用（对应规格 §7、§51）。
2. 企业微信回调协议细节（签名、加解密、XML 结构）只允许存在于
   `wecomcrypt.class.php` 与 `wecom/webhook.php`。
3. OAuth 协议细节只允许存在于 `wecom/wecom/oauth.php`。
4. 数据库表按 `llx_wecom_*` 命名，不引入"platform 字段"式的统一表设计。

## 触发重新评估的条件

出现以下任一情况时，重开此决策：

- 钉钉或飞书集成正式立项（有真实业务需求与测试企业凭据）；
- 出现第二个需要复用 WeComApi 形态的消费方（如 MCP/Skill 服务端）。

届时按"约束"一节列出的三个文件抽离接口，先写接口设计文档评审，再动代码。

## 后果

- V0.3 无代码层面的多平台改造，modWeCom 保持单平台独立模块。
- 若未来立项第二平台，需新建独立模块（如 modDingTalk）并遵守本 ADR 的抽离路径。
